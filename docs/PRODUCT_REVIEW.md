# 中国象棋 v3.1 审视报告

> 以产品经理视角审视现有单机中国象棋程序，先与市面优秀同类产品对标找差距，
> 再从代码层面找根因，最后给出并落地本次重构方案。
> 报告中的性能数字均为本机（Apple Silicon / Temurin 25）同一 JVM 下的实测值。

---

## 一、结论先行

v3.1 的**规则正确性和 AI 强度其实不差**——长将判负、三次重复、困毙、Pikafish 回退这些都做了，
perft 也和标准值吻合。真正的问题在另外三个方向：

1. **产品完整度**：缺了现代象棋软件的「基础设施」——认输/求和、计时、棋谱保存载入、复盘、
   翻转棋盘、拖拽走子、窗口缩放。这些不是锦上添花，而是用户判断「这是个完整软件还是课堂作业」的分界线。
2. **架构**：`ChessPanel` 一个类 1095 行，同时负责绘制、鼠标交互、AI 线程调度、提示、
   记谱、弹窗；所有类挤在默认包里，没有任何模块边界。
3. **性能地基**：走法生成把「合法性校验」实现成了「每个候选着法都重跑一遍全盘攻击检测」，
   导致搜索每深入一层都要付出数倍代价。AI 的强度上限被这个地基卡住了。

本次重构后：走法生成提速 **6.2 倍**（perft 节点数完全一致，正确性未变），
补齐 11 项产品能力，代码拆成 6 个包 23 个类，并补上构建脚本、CI 与 36 个自动化用例。

而「保存这盘棋」这种长期留存需求完全没有出口——这是产品层面最该补的洞。

## 三、代码层面的问题

### 3.1 架构

| # | 现象 | 影响 |
|---|---|---|
| A1 | `ChessPanel` 1095 行，绘制 + 输入 + AI 调度 + 提示 + 记谱 + 弹窗全在一类 | 任何改动都可能牵连其他职责；无法单独测试 |
| A2 | 14 个类全部在默认包，无 `package` | 没有模块边界，无法表达依赖方向，也不能被其他工程引用 |
| A3 | 无构建脚本、无 CI、测试是手写 `main` + 自定义断言 | 只能靠人记得跑 `java -cp bin ChineseChessTests`；PR 无法自动拦截回归 |
| A4 | 无包结构导致「工具类」和「核心类」混在一起（`MoveCodec` 与 `MoveNotation` 平级） | 阅读成本高 |

### 3.2 正确性

| # | 现象 | 影响 |
|---|---|---|
| B1 | 评估函数里将/士/象的 PST 表只填了红方半区（第 7–9 行），黑方取 `row` 直接命中 0 | **黑方将/士/象的位置分恒为 0**，红黑评估不对称，AI 执黑时对防线价值的判断系统性偏低 |
| B2 | 静态搜索在被将军时仍然使用「静态分 stand-pat」剪枝 | 被将局面被严重低估，容易出现「看不见对方杀棋」的低级失误 |
| B3 | 中等档只有 2 层 negamax，无置换表 | 与「中等」的预期不符，实际接近随机+吃子 |
| B4 | `FenCodec` 只能序列化，不能解析 | 无法从 FEN 摆残局、无法做残局模式 |

### 3.3 性能

| # | 现象 | 影响 |
|---|---|---|
| C1 | `getLegalMoves` 对每个候选着法调用 `isLegalMove`，后者又先调 `canMove` 重跑一遍棋子规则 | 同一套规则每条着法校验两次 |
| C2 | `isKingAttacked` 遍历**所有**敌子，对每个敌子调 `isValidMove(...,将帅格)` | 车/炮各自要扫一条射线，单次判定 ~数百次访存；而它每个节点要跑几十次 |
| C3 | 所有公开方法 `synchronized`，包括搜索热路径上的 `getPiece` / `getLegalMoves` | 每个节点上千次加锁，直接吃掉搜索深度 |
| C4 | `evaluate` 每次调用 `board.getPieces()`，该方法 `new ArrayList<>(pieces)` | 每个叶节点一次 32 元素拷贝 + 两次全盘攻击检测 |
| C5 | 重复局面裁决先 `clone()` 整盘再逐步 `undo()` 回溯 | 每次触发裁决都要复制历史 |
| C6 | 走法生成产生大量 `Move` 对象 | GC 压力，搜索越深越明显 |

**实测**（同一台机器、同一 JVM，从初始局面穷举合法着法总数）：

| 深度 | 节点数 | 旧实现 | 新实现 | 提升 |
|---|---|---|---|---|
| 1 | 44 | 1 ms | <1 ms | — |
| 2 | 1,920 | 7 ms | 2 ms | 3.5× |
| 3 | 79,666 | 83 ms | 15 ms | 5.5× |
| 4 | 3,290,240 | 1,481 ms | 240 ms | **6.2×** |

两边节点数完全一致，说明提速来自实现方式而非「少算了棋」。

### 3.4 交互与工程细节

| # | 现象 | 影响 |
|---|---|---|
| D1 | 棋盘 9 条竖线全部在河界处断开 | 与真实棋盘不符（最外两条应贯通），一眼假 |
| D2 | 每次播放音效都 `AudioSystem.getLine` + 新建 Clip + `Thread.sleep` | 连续走子时音效滞后于落子，且阻塞播放队列 |
| D3 | 状态栏混入 `(0,0)→(0,0)` 这类调试坐标 | 面向用户的文案带开发痕迹 |
| D4 | 将军闪烁定时器在无将军时也每 400ms 重绘全盘 | 空闲时持续占用 CPU |
| D5 | 结束对话框在 Swing 事件回调里同步弹出 | 模态阻塞，容易与 AI 回调交错 |

## 四、重构方案

### 4.1 目标结构

```
xiangqi/
├── app/    Main                      仅负责启动
├── core/   Board Piece Move          规则层，零 UI 依赖
│           Notation Fen Uci GameResult
├── ai/     Engine SearchEngine       引擎层，零 UI 依赖
│           Evaluation UciEngine AiPlayer
│           Difficulty SearchLimits SearchResult
├── game/   GameSession GameRecord    对局状态层，零 Swing 依赖
├── ui/     MainFrame BoardView       视图层，只做展示与输入
│           SidebarPanel RecordPanel
│           Theme SegmentedControl Ui Dialogs AiWorker
└── audio/  SoundBank                 音效
```

依赖方向严格单向：`ui → game → ai → core`。`core` 和 `ai` 完全不认识 Swing，
因此可以在无头环境里跑完整测试。

### 4.2 关键设计决策

**① 棋盘改为「单线程 + 副本」模型，去掉所有 `synchronized`**
搜索热路径上的锁是纯浪费：AI 本来就在 `board.copy()` 的独立副本上工作，与界面线程没有共享可变状态。
去掉锁后，代价从「每节点上千次加锁」变成「每步一次深拷贝」。

**② 走法用 `int` 打包**
`from(7bit) | to(7bit)<<7 | 被吃子类型(4bit)<<14`。搜索内部全程传 `int`，
只在根节点转成 `Move` 对象给界面。配合每层复用的 `int[]` 缓冲，搜索期间几乎零分配。

**③ 被将判定改为「反向攻击探测」**
不再「遍历所有敌子逐个试」，而是从将帅格向外看：
- 四个正交方向各扫一条射线，第一个遇到的敌子若是车/将则被攻击，第二个若是炮则被攻击；
- 八个马位反查，并检查对应的蹩腿点；
- 三个兵位反查（正面一格 + 过河后的左右）。
单次判定约 20 次查表，且顺带覆盖「将帅照面」。

> 仕/相被有意跳过：仕的活动范围是本方九宫、相不能过河，几何上永远够不到对方将帅所在的九宫。

**④ 将帅位置增量维护**
`kingSquare[2]` 在 `apply/revert` 时同步更新，判定被将时不再全盘扫描找将。

**⑤ 重复局面裁决走历史索引**
维护 `positionKeys`（每个历史节点之后的 Zobrist），三次重复时向前找上一次同局面，
只统计这一个循环内的将军次数，O(n) 且不需要克隆棋盘。

**⑥ 搜索层重写**
迭代加深 + PVS + 置换表（1M 项）+ 空着裁剪 + 后期着法削减（LMR）+ 杀手/历史启发 +
被将延伸 + 正确的静态搜索（被将时搜索全部应将着法，不用 stand-pat）。

低难度档用「根节点容忍度」实现：对每个根着法做全窗口搜索拿到真实分数，
再在与最优着法差距不超过 60 厘兵的着法里随机挑一手。这样既保留随机性，
又不会走出白送大子的着法（白送一个车会让分数掉 400 以上，直接落在容忍度之外）。
实测简单档会主动把车从卒口挪走、会吃白送的子，但看不到三步以上的战术。

**⑦ UI 拆成 MVC**
`BoardView` 只管画和收鼠标，合法性一律问 `Board`；`GameSession` 管状态迁移（悔棋/重做/复盘/计时）；
`MainFrame` 只做接线与持久化。AI 调度独立成 `AiWorker`：单线程执行 + 代际号丢弃过期结果 +
中止信号，切局/悔棋时旧搜索立刻让出 CPU。

**⑧ 构建与测试**
`build.sh` / `run.sh` / `test.sh` 三个脚本，零第三方依赖；GitHub Actions 跑同一套脚本。
测试分四组：规则（含 perft）、引擎、会话、渲染（离屏画图）。

## 五、验证

### 5.1 正确性

perft 深度 1–4 与公开基准值 **44 / 1920 / 79666 / 3290240** 完全一致。
这是走法生成器最硬的正确性证明：任何一个蹩马腿、塞象眼、将帅照面、自将判定的疏漏都会让数字对不上。

### 5.2 自动化用例（36 个，全部通过）

| 组 | 覆盖点 |
|---|---|
| 规则（19） | 初始/中局 FEN、UCI 往返、perft、七种棋子走法、牵制、照面、将死、困毙、三次重复、长将、随机对局悔棋还原、克隆隔离、记谱、越界、马后炮/蹩腿/过河兵攻击 |
| 引擎（7） | 吃白送车、一步杀、三档着法合法、时间上限、避免长将自伤、简单档不白送子、30 手自对弈 |
| 会话（7） | 悔棋成对回退、重做对称、复盘局面、认输、棋谱往返、计时、AI 回合判定 |
| 渲染（3） | 三套主题绘制、翻转生效、历史局面绘制 |

### 5.3 交互验证

- 离屏渲染三套主题生成截图（`docs/screenshot*.png`），确认无裁剪、无遮挡；
- 真实窗口冒烟：启动 → 切执黑 → AI 自动走开局 → 悔棋按钮正确置灰。

## 六、仍未做（路线图）

按「投入产出比」排序：

1. **残局闯关**：需要 FEN 解析（已有 `Fen.parse`）+ 关卡数据 + 胜负判定复用，成本低、留存价值高。
2. **开局库**：一个小型着法表即可让 AI 前 6–10 手更「像人」，同时避免开局阶段烧 CPU。
3. **引擎分析模式**：后台持续分析并给出评分曲线，配合已有的 `SearchResult` 不难。
4. **自动保存 / 崩溃恢复**：把 `GameRecord` 定时写盘即可。
5. **音效资源化**：当前是代码合成，换成真实木质采样会明显提升质感。
6. **色盲友好配色**：红/黑子改为「红/蓝」或加形状区分。
7. **开局/中局/残局分阶段评估**：现在是一套评估打天下，残局阶段对「兵」的价值判断偏保守。
